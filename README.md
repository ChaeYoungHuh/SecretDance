Console game term project for **CS-20200 Programming Principles (Spring 2026)**.

The game is implemented in **F#** on **.NET 10**.  
You control students who must keep dancing to gain score, but stop quickly when the professor turns around.

---

## 1) Environment and Prerequisites

- OS: macOS / Linux / Windows (any OS that supports .NET 10)
- SDK: **.NET 10**
- Terminal: any UTF-8 capable terminal (recommended for ASCII art rendering)

```bash
dotnet --version
```
---

## 2) How to Run

From repository root:

```bash
dotnet run
```

Optional:

```bash
dotnet build
```

---

## 3) Controls

- `A`: Start dancing, or switch to the next dance motion if already dancing (cycles: Motion 1 → 2 → 3 → 1 → ...)
- `D`: Stop dancing immediately (only effective while dancing)
- Any key on title screen: start game
- Any key on result screen: exit program

---

## 4) Game Overview

This is a real-time console rhythm-survival game.

- You gain score while dancing when the professor is writing on the board.
- A dance gauge naturally decreases over time.
- Dancing refills the dance gauge.
- If the gauge reaches zero, game ends since the class is over.
- The professor periodically turns around.
- If you keep dancing while the professor is fully turned, you are caught immediately.

---

## 5) Observable Requirements (Testable)

These requirements are intentionally concrete so reviewers can evaluate them directly.

1. The game starts with an animated title screen and waits for a key input.
2. During the game, student animation updates continuously and reacts to `A`/`D` key inputs.
3. Pressing `A` starts student nubzukis (넙죽이) to dance if idle, or switches to the next dance motion if they are already dancing. Motions cycle in order: Dance motion 1 → Dance motion 2 → Dance motion 3 → Dance motion 1 → ...
4. Pressing `D` while dancing immediately returns to idle. Has no effect when already idle.
5. A dance gauge is displayed as a bar with percentage and drain rate.
6. Gauge starts full at the beginning of each run.
7. While not dancing, gauge decreases continuously.
8. While dancing, gauge increases continuously (capped at 100%).
9. Score increases while dancing **only when the professor is looking at the board**.
10. Professor nubzuki turning sequence is visibly staged: front-facing -> transition (`profFrame3`) -> transition (`profFrame4`) -> fully turned (`profFrameTurn`) -> front-facing.
11. Turning timings include randomized jitter (small frame-level variation).
12. Turning interval gets shorter over elapsed time (difficulty ramps up).
13. Transition frame duration gets shorter over elapsed time (difficulty ramps up).
14. Fully turned hold duration gets shorter over elapsed time (difficulty ramps up).
15. If dancing is sustained during fully turned phase longer than the catch threshold (`max(0.15, 0.38 - 0.005*t - 0.0015*t^2)` seconds, where `t` is elapsed gameplay time in seconds), game ends immediately with CAUGHT.
16. If dance gauge reaches zero, game ends with `"The class is over.."`.
17. Result screen always shows final score.

## 6) Detailed Behavior

### 6.1 Scoring

- Score increases during active dancing at fixed time slices.
- Score does **not** increase while professor is fully turned or transition-turning.

### 6.2 Dance Gauge

- Initial gauge: `1.0` (100%)
- Initial drain rate: `0.062`
- Drain rate increases over time (periodic acceleration with upper bound).
- Refill while dancing is capped to max gauge.

### 6.3 Professor Timing

The professor state machine has these phases:

- `0`: front-facing
- `-1`: brief front-facing hesitation before turning (random)
- `1`: transition frame 3
- `2`: transition frame 4
- `3`: fully turned (danger phase)
- `4`: brief front-facing hesitation after turning (random)

Timing properties:

- Base turning interval shrinks as elapsed time increases.
- Transition durations shrink as elapsed time increases, with minimum bound.
- Fully turned duration shrinks as elapsed time increases, with minimum bound.
- Small random jitter is applied to avoid perfectly deterministic rhythm.

### 6.4 End Conditions

- **Caught ending**: sustained dancing during phase `3` exceeds catch threshold.
- **Class-over ending**: dance gauge reaches zero.

## 8) Requirement Changes and Justification

The final game keeps the same core concept from the proposal (dance while the professor is not watching, stop when watched), but several requirements were refined after implementation and play-testing.

### 8.1 Traceable Changes from Proposal

- **R1 (title animation interval change)**  
  Proposal version specified title-frame alternation every 1 second.  
  Final version alternates title frames every 0.5 seconds.
  **Why changed:** a 1-second cadence felt visually sluggish in terminal animation; 0.5 seconds made the start screen more readable and responsive without changing gameplay semantics.

- **R3, R4, R7, R9, R10, R12, R13, R14 (status model change)**  
  Proposal version used suspicion gauge + lives + fixed class timer.  
  Final version uses a single **dance gauge** and immediate end conditions (`caught` / `classover`) without lives.
  **Why changed:** in console rendering, managing three simultaneous resources (suspicion/time/lives) made readability poor and game feedback noisy. A single-resource model gave clearer, testable behavior and more stable pacing.

- **R8 (turn-around behavior change)**  
  Proposal version turned immediately and froze gauge for 2 seconds with warning text.  
  Final version introduces staged transitions (`profFrame3` -> `profFrame4` -> `profFrameTurn`) with shrinking durations.
  The warning banner text used in earlier iterations was removed, and the professor state is now communicated by frame transitions and color changes.
  **Why changed:** immediate turning and text-heavy warning output felt abrupt/noisy in terminal animation; staged turning and visual-only signaling made the state clearer while keeping the screen less cluttered.

- **R11 (scoring refinement)**  
  Proposal version scored during any dance state.  
  Final version scores only in front-facing phases, not while professor is effectively turning/watching.
  **Why changed:** this prevents rewarding unsafe behavior and better matches the intended "dance secretly" rule.

- **R15 (manual quit removal)**  
  Proposal included key-based exit flow after endings, and earlier versions had manual quit during gameplay.  
  Final version removes manual in-game quit and keeps exits tied to game outcomes plus final key press on result screen.
  **Why changed:** keeps termination semantics aligned with game rules and avoids accidental early termination during evaluation.

### 8.2 Difficulty-Tuning Changes

- Added controlled random timing jitter to turn events.
- Tuned turn interval shrink curves, transition durations, and catch threshold through repeated play-tests.
- Rebalanced dance-gauge drain/refill rates and acceleration.

**Why changed:** fixed deterministic timing was easy to exploit and produced repetitive play. The final tuned values maintain fairness while preventing trivial memorization.

These are requirement refinements of the same game design, not a change of project type.

## 9) LLM Usage Disclosure

This project used an LLM assistant during development.

### What the LLM was used for

- Debugging gameplay logic and timing behavior.
- Verifying timing-state edge cases for turn phases (`-1`, `1`, `2`, `3`, `4`) and score update conditions.

### What required manual correction / reprompt

- The first timing suggestions made early-game turn intervals too short, so the turn interval and transition-duration curves were reprompted and manually tuned after repeated play-testing.
- Edge-case behavior around turn states (`-1`, `1`, `2`, `3`, `4`) required manual checks to ensure score increments only in front-facing phases and catches occur only during the fully turned phase.

### Main limitation observed

- The LLM could suggest timing/state fixes quickly, but validating fairness and edge-case behavior still depended on manual play-testing.
